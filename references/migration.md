# Доведение существующей документации до скилла

Для проекта, где `docs/` уже есть - по старому `DOC_TEMPLATE.md` или просто россыпью. Цель:
добавить недостающее и убрать второй источник состояния, **не переписывая** существующие
файлы. Их размер и история - дело режима «сжатие», отдельным шагом после.

## 1. Что собрать

1. Линтер: `doc_lint.py <корень> --summary`. Числа по файлам - вход для плана.
2. Разделы «Состояние на <дату>» везде (`grep -rn "Состояние на" docs/ *.md`): где лежит
   свежее по каждому потоку.
3. Нестандартные метки с частотой: вывод линтера `--only LABEL`.
4. Потоки: папки `docs/projects/*` плюс «общее». Нет папок - потоки назвать по разделам
   `TASKS.md` и спросить.
5. Где сейчас таблица спринта (`grep -n "Спринт" docs/TASKS.md`) и на какой `§` ссылается
   `sprint-planning` (его `SKILL.md`).
6. Файлы в `docs/`, которые не укладываются в раскладку (`confluence/`, `html/`, `PROMPT.md`):
   что это и кому нужно.

## 2. План

Одним экраном, с числами строк. Записывать по «делай».

## 3. Что записать

1. **`CONVENTIONS.md §«Документы»`** - дописать, не переписывать:
   - строка «Активный спринт - `TASKS.md §N`» (N - тот номер, который уже зашит в
     `sprint-planning`; в скелете §3, в живом проекте может быть другой);
   - таблица «Местные метки» - по таблице переводов ниже;
   - таблица «Вне раскладки» - каталоги со своими правилами (`docs/confluence/`, `docs/html/`),
     линтер их пропускает;
   - таблица «Внешние корни» - откуда берутся ссылки на файлы вне `docs/` (клоны репозиториев,
     `~/.claude/skills/`), линтер проверяет их на диске, а если корня на машине нет - пропускает.
2. **Первая запись журнала с «Где мы».** Дата сегодняшняя, повод «документация доведена до
   скилла». Блок «Где мы» - по абзацу на поток, собранный из самых свежих разделов «Состояние
   на» этого потока, указателями, не пересказом. Старые «Состояния» смешивают факты и планы
   («тег ставить на X»): в «Где мы» факт идёт только с подтверждением в журнале (`grep`), иначе
   это «следующий шаг», а не «сделано». Остальные разделы «Состояние на» - в план
   сжатия как «дубль журнала», сейчас не трогать.
3. **Таблица спринта.** Если активный спринт лежит не в `§N` из `CONVENTIONS.md` - перенести
   содержимое в `§N`. Если в `§N` лежит закрытый спринт - поменять их местами: закрытый уезжает на
   старый номер активного с пометкой «перенесён из §N при доведении <дата>, до сжатия», а в шапке
   `§N` строка «ссылки на `§<старый>` до <даты> означают этот раздел». Это единственная правка
   `TASKS.md` при доведении.
4. **`CONTEXT.md`**: если нет раздела «Чего не умеет и что не сработало» - добавить в конец со
   следующим номером, пока с одной строкой: «заполняется при сжатии из журнала».
5. **`CLAUDE.md`**: строка таблицы «как вести документы» → `скилл /project-docs (репо
   <ссылка>)`, строка про `DOC_TEMPLATE.md` убрать, блок правил свести к пяти строкам из
   скелета. Файл промпта (`PROMPT.md`), если есть: сам промпт оставить, разделы «Состояние на» -
   в `ARCHIVE/` (их суть уже в записи журнала из п. 2), на месте две строки со ссылкой.
6. **`DOC_TEMPLATE.md`** → копия в `ARCHIVE/<дата>/` через `archive_copy.py`, на месте
   заглушка в три строки: «заменён скиллом `/project-docs`, оригинал в `ARCHIVE/<дата>/`».
7. **Метки-наследие.** Массово не заменять: `[СДЕЛАНО 06.10.2026]` у зачёркнутой задачи - это
   статус, не факт, а `[ОБНОВЛЕНО <дата>]` - след правки, который при сжатии уйдёт в журнал вместе
   с абзацем. Вместо замены - вторая таблица в «Местных метках» `CONVENTIONS.md` с подписью
   «наследие до сжатия <дата>, в новых записях не использовать», куда входят все нестандартные
   метки с частотой больше 1 (вывод линтера `--only LABEL`). Разовые (`[УРОК С КИТОВ]`) - оставить
   линтеру как ошибки, их поправят при сжатии по таблице переводов ниже.
8. Запись в `ARCHIVE/README.md` и строка в записи журнала: что сделано, что отложено до сжатия.

## 4. Таблица переводов меток

Общая для всех проектов; местное - добавить в план и в «Местные метки».

| Было | Стало | Почему |
|---|---|---|
| `[СДЕЛАНО]` | `[ФАКТ]` с якорем или МР | это и есть факт о сделанном |
| `[ВНИМАНИЕ]` | `[ВАЖНО]` | синоним |
| `[РЕШЕНИЕ]`, `[РЕШЕНО]` | `[РЕШЕНИЕ <дата>]` | в наборе, нужна дата |
| `[ОТМЕНЕНО]`, `[ОТМЕНЁН]`, `[СНЯТО]` | `[ОТВЕРГНУТО <дата>]` | в наборе |
| `[ЗАКРЫТ]`, `[ЗАКРЫТО]` | `[ОТВЕТ <дата>]` для вопроса; для задачи - строка в журнале | закрытие - это ответ или итог |
| `[ДЕЛАТЬ]`, `[ПЛАН]`, `[СОГЛАСОВАТЬ]` | без метки; это задача - строка в `TASKS.md` | метка источника, не статус |
| `[ОБНОВЛЕНО]`, `[ИЗМЕНЕНО]`, `[ИЗМЕНЕНИЕ]`, `[УТОЧНЕНО]`, `[УТОЧНЕНИЕ]`, `[ДОПОЛНЕНО]`, `[ДОПОЛНЕНИЕ]`, `[НОВОЕ]`, `[ПОПРАВКА]` | в живых файлах - убрать метку, абзац остаётся; это след истории | уйдёт в журнал при сжатии |
| `[ПРОВЕРЕНО]` | `[ФАКТ]` с указанием, чем проверено | то же |
| `[СПОРНО]` | `[ДООПРОС]` с владельцем | спорное - это невыясненное |
| `[БЕЗОПАСНОСТЬ]`, `[ИДЕЯ]`, `[В СТАТЬЮ N]`, `[НЕ В СТАТЬЮ]` и прочее со смыслом, которого в наборе нет | местная метка в `CONVENTIONS.md` | у проекта есть на это причина |

Таблица применяется при сжатии к живым файлам (`CONTEXT`, `TASKS`, `CONVENTIONS`, `CLAUDE.md`), по
одному разделу за раз, с записью в опись. Переносимый в `changelog/` и `notes/` текст не трогается.
Метка, которой в таблице нет, молча не снимается: строка в план «`[X]` → `[Y]`, потому что» и либо
в «Местные метки» проекта, либо в эту таблицу через «Правка скилла».

## 5. После

- `doc_lint.py <корень> --summary`: ошибок по меткам и «Состояние на» в живых файлах нет;
  бюджеты пока красные - это нормально, их закрывает «сжатие».
- Следующий шаг - «аудит», потом «сжатие», начиная с журнала.
